# 免费版 AI 智能化评审工具：详细开发设计书

版本：1.0\
目标读者：AI 编程代理、全栈开发人员、产品负责人\
产品名称暂定：AI Business Opportunity Assessment\
目标市场：澳大利亚中小企业（SME），但评估入口不限定行业\
文档状态：MVP 实施规格

## 0. 给开发 AI 的执行指令

请把本文档视为产品需求与技术验收基准。先输出实施计划和数据模型，再按阶段开发；不得擅自删除业务规则、虚构客户数据或把示例
ROI 作为事实。任何 AI
生成内容都必须基于结构化输入，并标明"用户提供的数据""系统计算值""模型推断""待验证假设"。

实施顺序： 1. 建立项目骨架、环境配置、数据库迁移、测试框架。 2.
完成动态问卷与自动保存。 3. 完成确定性机会匹配、可行性门槛与价值计算。
4. 完成结构化 AI 报告生成。 5. 完成邮箱留资、PDF 报告、后台线索查看。 6.
加入安全、隐私、日志、限流和端到端测试。 7. 不要在第一版开发自动规划复杂
Agent、真实业务系统写入、OAuth 连接器或精确 ROI 承诺。

## 1. 产品目标与非目标

### 1.1 目标

-   让企业在 5--8 分钟内完成自助评估。
-   在报告中识别 2--3 个与该企业回答相关的 AI/自动化机会。
-   对优先级最高的机会提供一张个性化的 Agent/自动化概念设计卡。
-   给出透明的价值区间、关键假设、实施条件、风险和 90 天高层路线图。
-   通过用户主动提交邮箱，发送完整 PDF，并形成可跟进的销售线索。
-   用规则和可解释计算保障一致性；LLM
    负责归纳、解释和个性化表达，不负责自行编造评分或 ROI。

### 1.2 非目标

-   不接入客户真实系统、不读写 ServiceM8、Tradify、simPRO 或其他 SaaS。
-   不承诺精确 ROI，不把可释放工时等同于现金节省。
-   不自动生成可直接部署的完整 Agent 工程蓝图。
-   不提供法律、税务、安全认证或合规审计结论。
-   不因"AI 热点"强行推荐
    AI；普通规则自动化、现有软件功能或暂不行动都可以是结论。

## 2. 推荐技术方案

可由开发团队按现有能力调整，但必须保留接口契约和确定性业务逻辑。

-   前端：Next.js + TypeScript + React。
-   表单校验：Zod；表单状态可使用 React Hook Form。
-   后端：Next.js Route Handlers（MVP 可先采用同一代码库）。
-   数据库：PostgreSQL；托管可选 Supabase 或等价服务。
-   AI：通过统一 LLM adapter 调用模型，支持结构化 JSON
    输出；模型名称与密钥放环境变量。
-   PDF：由 HTML 报告模板生成 PDF；必须同时保留网页报告。
-   邮件：通过可替换的邮件服务适配器发送验证邮件和报告链接。
-   部署：支持预览环境、生产环境、数据库迁移和回滚。
-   测试：单元测试、API 集成测试、浏览器端到端测试。

不要把 API 密钥放在浏览器端。不要将模型输出直接拼接进 SQL、HTML 或命令。

## 3. 用户流程

1.  落地页：说明评估能得到什么、预计用时、数据用途。
2.  开始评估：生成 assessment_id 和匿名 session token。
3.  动态问卷：按分支展示问题；自动保存；允许"不确定/不知道"。
4.  计算评估：服务端校验回答并执行规则引擎。
5.  生成预览：展示企业概况、优先机会摘要、初步价值、关键风险。
6.  留资：用户主动填写姓名、工作邮箱、公司名（公司名可选）；营销订阅必须单独、非预勾选。
7.  生成完整报告：服务端生成结构化报告并生成 PDF。
8.  报告交付：展示下载链接并通过邮件发送安全链接。
9.  线索后台：授权员工查看线索、评估摘要、用户同意状态和跟进状态。

不要强制用户先留邮箱才能看到所有价值。建议报告预览展示至少一个具体发现；留资后提供完整报告。

### 4.2 分支规则

-   若 bottleneck 包含"文档/表单处理"，追加
    document_type、每月文件量、文件格式和错误后果。
-   若包含"销售/询盘/报价跟进"，追加询盘来源、每周询盘量、当前响应时间、报价量和跟进方式。
-   若包含"客户服务"，追加渠道、重复问题比例、服务时间要求、升级给人工的比例。
-   若包含"知识查找/内部问答"，追加知识来源、更新频率、权限是否分级、错误答案后果。
-   若包含"跨系统录入"，追加源系统、目标系统、是否支持
    API/导出、当前人工复制粘贴次数。
-   若涉及敏感数据或高风险动作，必须追加数据访问范围、审批人和错误影响。
-   对"不知道"不惩罚用户，但降低估算置信度，并在报告中列出需要补充的数据。
-   只展示与前面答案相关的问题；提供进度提示和返回修改能力。

### 4.3 数据输入原则

-   数值问题优先使用区间或可选"不知道"；如接受精确数字，限制合理范围并校验。
-   所有金额默认 AUD；界面明确说明税前/税后或成本口径。
-   不收集不必要的客户姓名、客户内容、密码、API key 或文件原文。
-   保存每个问题的回答版本，以便问题变化后仍能解释旧报告。

## 5. 业务机会库

机会模型必须配置化。每个机会至少有：id、名称、适用触发条件、排除条件、所需输入、评分规则、价值公式、实施前置条件、风险门槛、推荐动作、证据要求。

第一版包含以下 7 个机会：

1.  文档处理与信息提取：从邮件/ PDF /表单抽取字段、分类、生成记录草稿。
2.  询盘分流与跟进：分类询盘、提取需求、生成回复草稿、提醒跟进。
3.  客户服务辅助：从批准的知识库生成建议回复并升级复杂问题。
4.  企业知识检索：对内部文档进行带来源的检索问答。
5.  运营工作流自动化：规则触发、数据校验、任务创建和提醒。
6.  报告与数据分析：汇总结构化数据、生成周期性经营摘要。
7.  会议/沟通后续任务：总结沟通、提取待办并生成任务草稿。

### 5.1 机会匹配评分

对每个机会分别评分，不能先算一个企业总分再推荐全部方案。

建议初始权重（0--100）： - 痛点匹配：0--30 - 任务频率/工作量：0--20 -
流程可标准化程度：0--15 - 数据可获得性：0--15 - 系统可连接性：0--10 -
负责人/执行准备度：0--10

每项映射到 0--该项满分。缺失数据不自动当作零；用 unknown 标记并降低
confidence。评分阈值仅用于排序，不是行业基准： - 70--100：优先验证 -
45--69：有潜力，先补条件 - 0--44：暂缓/需进一步发现问题

### 5.2 硬性风险门槛

以下情况不得被高分抵消： - 用户希望 AI
在无人审核下执行高影响财务、法律、雇佣或安全关键动作。 -
数据权限不清楚，且方案需要访问敏感数据。 -
没有合法/适当的数据使用依据或无法确认数据处理安排。 -
错误后果高且没有人工复核、审计或回滚机制。 -
核心软件不可访问且没有合理替代路径。

结果可以是"先做流程整理/权限治理/规则自动化"，而不是推荐 Agent。

## 6. 价值计算引擎

### 6.1 基本公式

现有年度任务工时 = 每周任务次数 × 每次分钟数 ÷ 60 × 52。

潜在释放工时 = 现有年度任务工时 × 预计可减少比例。

潜在人工时间价值 = 潜在释放工时 × 每小时综合人工成本。

年度净收益（如数据足够） = 可兑现现金节省 + 可量化新增贡献毛利 +
可避免损失 − 年度软件/运行成本。

首年 ROI = (首年收益 − 一次性实施成本 − 首年运行成本) ÷
(一次性实施成本 + 首年运行成本)。

若分母为 0、关键输入缺失或收益不可兑现，不输出百分比 ROI。

### 6.2 估算规则

-   预计可减少比例必须来自可配置假设范围，不得由 LLM 任意编造。
-   对没有行业实证数据的机会，明确标注"规划假设，需通过试点验证"。
-   输出保守/基准/乐观情景，并解释变量。
-   人工时间价值与现金节省必须分开显示。
-   不得把收入金额直接当作新增利润；需要贡献毛利或合理替代指标。
-   不把减少错误的全部潜在金额当作可避免损失，需乘以可避免比例和证据置信度。
-   报告显示输入数据、公式、假设、遗漏项和置信等级（低/中/高）。
-   置信等级规则由确定性逻辑决定：关键输入完整性、数据来源和指标追踪程度；不能让
    LLM 自评置信度。

## 7. 报告生成规范

### 7.1 报告章节

1.  执行摘要：企业现状、首要目标、最重要发现。
2.  2--3 个机会：问题、当前流程、预期改善、适配理由。
3.  优先机会概念设计：目标、输入、处理步骤、系统动作、人工确认、异常处理。
4.  价值估算：现状工作量、情景区间、公式、假设、置信度。
5.  可行性分析：流程、数据、系统、人员。
6.  风险与边界：数据、权限、错误影响、人工审核。
7.  90 天高层路线图：0--30 天验证；31--60 天试点；61--90 天评估扩展。
8.  下一步：补充数据/预约付费深度审计。
9.  方法说明：这是初步评估，不是保证收益或正式安全审计。

### 7.3 AI 生成要求

AI 输入只能包括必要的结构化答案、机会引擎结果、计算引擎结果和报告
schema。要求模型返回 JSON，不接受模型自行计算财务指标。 模型不得： -
虚构客户事实、系统 API 能力、行业基准、软件价格或节省率。 -
将建议表述为已验证结论。 - 输出未经用户提供或规则引擎计算的 ROI。 -
忽略风险门槛。 - 推荐与回答不相关的 Agent。

若 JSON
校验失败，最多重试一次；再次失败则使用确定性模板降级生成，不能让用户看到原始模型错误。

## 8. API 契约（示例）

-   `POST /api/assessments`：创建评估，返回
    assessment_id、session_token。
-   `GET /api/assessments/:id`：恢复问卷；必须验证 session_token。
-   `PUT /api/assessments/:id/answers`：保存部分回答。
-   `POST /api/assessments/:id/evaluate`：运行规则引擎与价值计算，返回预览。
-   `POST /api/assessments/:id/lead`：提交邮箱及同意状态。
-   `POST /api/assessments/:id/report`：生成报告，返回报告状态与安全链接。
-   `GET /api/reports/:token`：读取报告；token 应不可猜测且可过期。
-   `POST /api/admin/login`：由选定身份服务处理，不自行实现弱密码认证。
-   `GET /api/admin/leads`：分页线索列表，仅授权角色访问。
-   `PATCH /api/admin/leads/:id`：更新跟进状态与内部备注。

所有 API
必须校验输入、权限、速率限制和错误响应格式。报告生成接口应幂等，避免重复调用产生重复邮件。

## 10. 隐私与安全

-   在收集邮箱前显示清晰的隐私说明和数据用途。
-   报告交付同意与营销订阅分开；营销选择不得预勾选。
-   仅收集完成评估所需的数据；设置保留期、删除流程和访问控制。
-   使用 TLS、服务端密钥、数据库最小权限、限流和安全日志。
-   对邮件、文件名和用户文本进行输出编码，防止 XSS。
-   对提示注入做防护：用户回答只作为数据，不作为系统指令。
-   采用澳大利亚适用隐私法规与客户合同要求进行法律审查；不得声称工具天然符合某项法律。
-   生产环境前完成威胁建模、备份/恢复测试和依赖漏洞扫描。

## 11. 管理后台

最小功能： -
线索列表、创建时间、公司、邮箱、评估状态、主要机会、预算/时间意向。 -
查看评估摘要与报告。 - 更新跟进状态：new / contacted / discovery_booked
/ qualified / not_fit / converted。 - 导出 CSV（仅授权人员）。 -
查看同意版本与时间。 - 不展示不必要的敏感原始内容。

## 12. 可观测性与产品指标

记录匿名化事件： - assessment_started - question_answered（只记
question_id，不记敏感答案） - assessment_completed - preview_viewed -
lead_submitted - report_generated - report_opened - discovery_clicked

关键指标： - 开始到完成转化率 - 中途退出问题位置 - 留资率 - 报告打开率 -
合格线索比例 - 付费审计转化率 - 机会推荐被专家判定相关的比例

不得把完成问卷数量当作唯一成功指标。

## 13. 测试与验收

### 单元测试

-   ROI 公式正确，边界值、缺失值、零值处理正确。
-   风险门槛可覆盖高机会分。
-   "不知道"降低置信度而不是被默认为零。
-   每个机会匹配条件有正例、反例。
-   报告中的数字必须与计算结果完全一致。

### API 测试

-   未授权用户不能读其他 assessment。
-   过期 token 无法访问报告。
-   重复生成报告不重复创建线索或邮件。
-   非法字段、超长文本、错误邮箱、异常数值均被拒绝或规范化。

### E2E 测试

-   完成一份通用评估并生成报告。
-   不同分支出现正确的后续问题。
-   高风险答案触发风险提示，不推荐无人审核 Agent。
-   不留营销同意也能获得用户请求的报告。
-   邮件失败时仍能在页面看到报告生成状态或重试入口。

### 发布验收标准

-   主要流程在桌面与移动端可用。
-   报告可在网页查看并导出 PDF。
-   所有计算均可追溯到输入与公式。
-   AI 生成失败时可降级，不丢失用户回答。
-   不存在客户端暴露密钥、未授权报告访问或可直接执行的模型生成代码。
-   至少为每个机会模型建立自动化测试。
-   生产部署、备份、错误监控和隐私说明均已配置。

## 14. MVP 开发分期

-   P0：问卷、自动保存、机会规则、价值计算、HTML 报告。
-   P1：邮箱留资、PDF、邮件交付、后台线索。
-   P2：事件分析、内容版本管理、实验不同落地页。
-   暂不做：真实 SaaS 连接、自动 Agent 部署、复杂多 Agent
    协作、自动合同/财务动作。

## 15. 完成定义

开发 AI 在提交代码前必须提供： 1. 项目运行说明和
`.env.example`（不含真实密钥）。 2. 数据库迁移和种子数据。 3. API 文档。
4. 机会规则和 ROI 公式说明。 5. 自动化测试与测试结果。 6.
本地运行、部署、回滚步骤。 7. 已知限制与安全检查清单。
